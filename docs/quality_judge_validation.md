# 쇼더스 대본 품질 판정기: 기준, 판정 방식, 검증

조희진 · 2026-11-22

## 0. 요약

- **무엇을 만들었나.** 쇼더스가 만든 대본 초안과 원문을 받아 `render`, `regenerate`, `human_review` 가운데 하나를 내는 판정기다. 대본을 승인하기 전, 곧 음성 합성과 렌더에 돈이 들기 전에 놓는다.
- **좋은 대본을 무엇으로 봤나.** "렌더한 뒤에 다시 손댈 이유가 없는 대본"이다. 분량이 맞고, 원문과 같은 말을 하고, 빠진 내용 때문에 뜻이 달라지지 않은 대본이다.
- **어떻게 판정하나.** 분량과 형식은 규칙으로 본다. 뜻은 LLM에 섹션마다 예/아니오로 묻고, 근거로 댄 원문 구절이 원문에 실제로 있는지 코드가 글자로 다시 확인한다. 확신할 수 없으면 통과시키지 않고 사람에게 보낸다.
- **믿을 근거는 무엇인가.** 결함을 하나씩만 심은 변형본에서, 판정기를 고정한 뒤 처음 돌린 6개 모두 결함을 심은 바로 그 섹션을 짚었다. 조정에 쓴 묶음에서는 3회 반복 30번 가운데 29번 짚었고, 나머지 1번은 답의 형식이 깨져 사람 확인으로 갔다. 결함이 없는 대조군은 3번 모두 통과했다.
- **어디가 약한가.** 내가 직접 매긴 라벨과 견주면, 통과시킬지 말지가 실제 초안 11편 중 6편에서만 맞았다. 어긋난 5편 가운데 2편은 판정기의 설계 결함(사실을 말하지 않는 섹션에까지 원문 근거를 요구했다), 1편은 분량 규칙, 1편은 판정기가 나보다 엄격해서, 1편은 판정기에 없는 기준 때문이다. 이 판정기는 틀린 대본을 거르는 장치이지 좋은 대본을 고르는 장치가 아니다. 고정 뒤에 드러난 문제는 고치지 않고 4.2에 남은 일로 적었다.

## 1. 좋은 대본의 기준

### 1.1 기준을 지어내지 않고 서비스에서 읽었다

기준을 세우기 전에 쇼더스의 화면, 도움말, 요금 안내, 약관, 공개된 도구 목록을 읽었다. 약관 11조가 서비스 역설계를 금지하므로 공개된 면만 봤다. 여기서 기준의 뼈대가 나왔다.

| 서비스에서 읽은 것 | 출처 | 기준에 준 것 |
|---|---|---|
| "회사는 원본 콘텐츠의 사실관계를 검증하지 않습니다. 생성물의 내용이 원본과 다르거나 부적절하다고 판단되면..." | 이용약관 | 충실도의 기준은 "참인가"가 아니라 "원문과 같은가"다 |
| "첫 섹션(훅)이 시청 지속을 좌우합니다" | 도움말 | hook을 가장 엄격하게 본다 |
| 대본은 draft로 먼저 생기고, 승인하면 TTS, 정렬, 장면 계획, 배경 소재 준비가 이어진다 | 도구 목록 | 판정기 자리는 draft와 승인 사이다 |
| 승인 조건은 3개뿐이다: 섹션당 5~300자, 첫 섹션이 훅, 나레이션 100초 이내 | 2단계 화면 | 서비스가 막는 것은 형식뿐이다. 내용은 아무도 보지 않는다 |
| 초안은 무료, 영상이 완성되면 7크레딧 차감 | 직접 만들어 확인 | 초안 단계에서 거르면 7크레딧과 수 분을 아낀다 |
| "qc:null = could not judge, NOT a pass" | 도구 목록 | 판정 불가는 통과가 아니다 |

쇼더스에는 이미 품질 장치가 있다. 원문과 다른 숫자와 발언자에 다는 "[사실 확인]" 검수, 렌더 뒤의 QC 리포트, 완성본을 6축으로 채점하는 품질 리뷰다. 그래서 과제의 빈자리를 "판정이 없다"가 아니라 "승인 전에, 대본만 보고, 하나의 행동으로 이어지는 판정이 없다"로 좁혔다. 내가 모은 초안 12편의 2단계 화면에는 기존 검수 표시가 하나도 없었다.

### 1.2 정의

좋은 대본은 렌더한 뒤에 다시 손댈 이유가 없는 대본이다. 세 가지로 나눴다.

| 묻는 것 | 실패하면 | 근거 |
|---|---|---|
| 분량이 30~45초인가, 형식이 맞는가 | `regenerate` | 과제 메일의 목표 구간, 쇼더스 승인 조건 |
| 섹션마다 원문과 같은 말을 하는가 (없는 사실, 바뀐 방향, 커진 정도, 바뀐 확실성, 단정한 인과, 빠진 조건) | `regenerate` | 약관의 "원본과 다르거나" |
| 빠진 내용 때문에 남은 문장의 뜻이 달라졌는가 | `regenerate` | 초안 12편을 읽고 추가했다 (1.3) |
| 끝이 마무리되는가, 역할 이름과 내용이 맞는가 | 경고만 붙인다 | 초안 12편을 읽고 낮췄다 (2.4) |

hook이 끌리는가, 재미있는가는 기준에서 뺐다. 정답을 만들 방법이 없어서다. 이 판정기가 보는 것은 "틀리지 않았는가"이고 "잘 썼는가"가 아니다.

### 1.3 대본을 읽고 기준을 고쳤다

원문 12개를 직접 썼다. 뉴스형, 블로그, 커뮤니티 글, 제품 소개에 3개씩이고, 원문마다 생성기가 틀리기 쉬울 것 같은 점을 하나씩 심었다(주제 둘, 화자 여럿, 비꼬는 말투, 조건이 붙은 가격 등). 쇼더스 입력 화면이 권리를 가진 글만 넣으라고 고지하므로 남의 기사는 쓰지 않았다. 대본을 보기 전에 "이렇게 왜곡될 것이다"라는 예상을 원문마다 적어 두었다.

결과는 예상과 달랐다.

- dev 5편에 적어 둔 왜곡 예상 22개 가운데 온전히 맞은 것은 1개, 약하게 맞은 것은 5개였다. (채점은 AI 도구가 했다.)
- 숫자, 이름, 날짜는 dev 6편 모두 원문과 같았다. 생성기는 어려운 부분을 틀리는 대신 뺐다.
- 원문과 뜻이 어긋난 곳은 hook에 있었다. 폐관 시간을 늦췄다는 원문이 "문을 늦게 열었더니"가 됐고, 3% 감소가 "한산해졌어요"가 됐다.

그래서 기준을 이렇게 옮겼다.

| 처음 생각 | 고친 뒤 |
|---|---|
| 숫자와 이름을 원문과 대조하는 규칙이 중심이다 | 숫자 대조는 안전망으로만 둔다. 중심은 "같은 뜻, 같은 정도인가"다 |
| 빠진 내용이 있으면 결함이다 | 30초 요약에서 빠지는 것은 당연하다. 빠져서 뜻이 달라질 때만 결함이다 |
| 장면은 6~7개가 보통이다 (도움말 예시) | 초안 12편 중 9편이 5섹션이었다 |

기준을 먼저 세우고 대본을 봤다면, 거의 일어나지 않는 왜곡을 잡는 판정기를 만들었을 것이다.

## 2. 판정 방식

### 2.1 구조

```
원문 + 대본 초안
      |
  [규칙 층]  분량 30~45초, 첫 섹션 훅, 섹션당 5~300자
      |  탈락 -> regenerate (LLM을 부르지 않는다)
      v
  [LLM 층]   섹션마다: 사실이 원문에 있는가 / 같은 뜻인가 / 근거 구절 / 무엇이 다른가
             전체: 빠져서 뜻이 달라졌는가 / 끝이 마무리되는가 / 역할 불일치 / 지시문이 있었는가
      |
  [코드 대조] 근거 구절이 원문에 글자로 있는가, 대본의 숫자가 원문에 있는가
      |
  행동 하나: render / regenerate(사유) / human_review(사유)
```

행동을 정하는 규칙은 이렇다.

| 상황 | 행동 |
|---|---|
| 규칙 탈락, 또는 LLM이 어느 섹션을 "원문에 없다"나 "뜻이 다르다"고 함, 또는 "빠져서 뜻이 달라졌다"고 함 | `regenerate` |
| LLM의 답을 읽을 수 없음(한 번 다시 물은 뒤에도), LLM이 문제없다고 했지만 근거 구절이 원문에 없음, 대본의 숫자가 원문에 없는데 LLM은 문제없다고 함, 원문이나 대본에 검수자를 향한 지시문이 있음 | `human_review` |
| 그 밖 | `render` (경고가 있으면 함께 낸다) |

고칠 것이 분명하면 다시 뽑게 하고, 판정기 자신이 미덥지 않으면 사람에게 넘긴다.

### 2.2 출력 예

모은 초안 가운데 1번(도서관 야간 개방 기사)의 실제 출력이다. 전체는 `examples/pair_01_library.output.json`에 있다.

```json
{
  "action": "regenerate",
  "est_sec": 32.4,
  "regenerate_reasons": [
    {
      "layer": "llm",
      "code": "MEANING_CHANGED",
      "section": 0,
      "message": "원문은 폐관 시간을 늦췄다고 했는데 '문을 늦게 열었더니'로 바뀌었고, 3% 감소를 '한산해졌다'로 과장했다.",
      "source_quote": "반면 어린이 자료실 이용은 같은 기간 3% 줄었다"
    }
  ],
  "review_reasons": [],
  "warnings": [
    {"code": "ROLE_MISMATCH", "section": 4, "message": "섹션 5의 역할과 내용이 맞지 않는다"}
  ]
}
```

사유에 섹션 번호와 원문 구절이 들어 있어서, 다시 뽑을 때 생성기에 그대로 돌려줄 수 있다.

### 2.3 규칙 층의 숫자는 재서 정했다

- **예상 발화 시간.** 발화 속도를 가정하지 않고 쇼더스 화면에서 쟀다. 섹션 59개 모두에서 화면의 예상 초가 "공백 포함 글자 수 ÷ 7.0을 0.1초로 반올림한 값"과 정확히 같았다(Aria, 1.1배속). 그래서 분량 검사는 서비스에 묻지 않고 글자 수로 계산한다. 30~45초는 210~315자다.
- **숫자 안전망.** 대본에 있는 아라비아 숫자가 원문에 있는지 본다. 원본 초안 12편에서는 한 번도 걸리지 않았다(오탐 0). 변형본에서는 원문에 없는 숫자로 바꾼 2개를 잡았고, 원문의 다른 자리에 있는 숫자로 바꾼 것(41%를 14%로. 원문에 "14일"이 있다)은 잡지 못했다. 그것은 LLM 층이 잡았다. 이 규칙만으로는 부족하다는 것을 변형본으로 확인한 셈이다.

### 2.4 트레이드오프

**분량을 탈락 조건으로 뒀다.** 초안 12편 중 7편이 30초에 못 미친다(중앙값 28.45초, 최소 24.6초). 45초를 넘은 것은 없다. 입력 화면은 "35초 기준"이라고 안내한다. 30~45초를 그대로 탈락 조건으로 쓰면 초안의 절반 넘게 걸러진다. 경고로만 두거나 하한을 25초로 낮추는 안도 놓고 봤지만, 과제가 준 조건을 판정기가 임의로 풀지 않기로 했다. 대신 사유에 "약 30자 부족"처럼 모자란 양을 적어 다시 뽑을 때 쓸 수 있게 했다. 실제로 붙인다면 이 숫자는 운영하는 쪽이 정할 값이고, 코드에서는 상수 두 개다.

**규칙에서 탈락하면 LLM을 부르지 않는다.** 분량 미달인 7편에는 LLM 비용이 들지 않는다. 대신 그 대본의 내용 문제는 다시 뽑은 뒤에야 본다. 두 번 도는 경우가 생길 수 있다.

**점수 대신 예/아니오와 근거 인용.** 1~10점은 왜 6점인지 설명하지 못하고 실행마다 흔들린다. 예/아니오는 행동으로 바로 이어지고, 근거 구절은 코드가 원문과 대조할 수 있다. 치르는 값도 있다. 모델이 구절을 조금 바꿔 적으면 문제없는 대본이 사람 확인으로 간다.

**끝맺음과 역할 불일치는 경고로만 둔다.** 초안 12편 모두 마지막 섹션의 역할이 "행동 유도"였는데, dev 6편 가운데 시청자에게 무엇을 하라고 말하는 문장은 없었다. 역할 이름이 내용이 아니라 위치로 붙는 것으로 보인다. 이것을 탈락 조건으로 두면 거의 모든 대본이 탈락한다.

**모델은 Sonnet을 골랐다.** 같은 프롬프트(v3)로 dev 묶음을 3회씩 돌려 비교했다.

| | Haiku | Sonnet |
|---|---|---|
| 결함 변형본에서 결함을 심은 섹션을 짚음 | 30/30 | 29/30 (1회는 답 형식 오류로 사람 확인) |
| 결함을 심지 않은 섹션을 추가로 짚음 | 8회 | 0회 |
| 결함 없는 대조군을 통과시킴 | 2/3 | 3/3 |
| 3회의 사유까지 같은 대본 | 4/18 | 10/18 |
| 호출당 비용 (test 묶음, 도구가 보고한 값) | 약 0.0025달러 | 약 0.025달러 |

Haiku는 10배쯤 싸고 결함도 잘 찾지만, 문제없는 곳을 함께 짚는다. 이 판정기의 출력은 "사유를 붙인 재생성"이라, 틀린 사유가 섞이면 생성기가 멀쩡한 문장을 고치게 된다. Sonnet의 비용은 대본당 0.013~0.025달러, 응답은 중앙값 4~8초였다. 렌더 한 편이 7크레딧(충전 단가로 700원)이니 대략 그 몇십 분의 일이다.

**프롬프트는 dev에서 두 번 고쳤다.** 첫 판(v1)은 과민했다. Haiku가 결함 없는 대조군을 떨어뜨렸고, 3% 감소를 "조금 줄었다"고 쓴 것까지 정도를 바꿨다고 봤다. v2에서 "덜 자세한 것, 유보를 그 섹션에서 다시 말하지 않은 것, 순서만 말한 것은 문제가 아니다"를 명시했다. v3에서는 섹션 수만큼 빠짐없이 답하라는 문장을 더했다. Sonnet이 결함 섹션까지만 답하고 멈추는 일이 있어서다. 그 뒤 형식이 맞지 않으면 한 번 다시 묻게 하고 고정했다.

## 3. 검증

### 3.1 판정기가 아닌 것에 기댔다

판정기가 옳다는 것을 판정기의 출력으로 보일 수는 없다. 네 가지에 기댔다.

1. **결함을 하나씩만 심은 변형본.** 바탕 대본의 한 군데만 바꿨으므로 정답(어느 섹션이 왜 틀렸나)을 안다. 바꾼 문자열은 `data/mutants/build_mutants.py`에 그대로 적혀 있다.
2. **결함 없는 대조군과 원본 초안.** 문제없는 대본을 떨어뜨리지 않는지 본다.
3. **묶음 나누기.** 원문 12개를 대본을 보기 전에 dev 6개와 test 6개로 나눴다. 기준과 프롬프트는 dev만 보고 고쳤다. 판정기를 고정(`eval/FREEZE.md`)한 뒤 test를 한 번만 돌렸고, 그 결과를 보고 코드를 고치지 않았다.
4. **사람 라벨.** 판정기 결과를 보기 전에 내가 직접 매겼다. (3.3)

표본이 작아서 결과는 비율이 아니라 개수로 적는다. 모든 숫자는 `python3 eval/summarize.py`로 다시 계산할 수 있고, 모델의 원래 답은 `eval/results/`에 있다.

행동이 같았던 6편에서도 이유는 대부분 달랐다. 나는 02번을 주제가 둘이라서, 04번과 08번을 행동 유도 때문에, 07번을 말투 때문에 걸렀다. 판정기는 넷 다 분량에서 걸렀다. 이유까지 같았던 것은 09번 하나다(반복해서 샀다는 암시).

라벨을 매기면서 판정기에 없는 기준이 세 가지 드러났다.

1. **마지막 섹션이 실제로 행동을 권하는가.** 04, 08, 11번에서 세 번 지적했다. 판정기는 역할 불일치를 경고로만 붙인다(2.4). 내 판단과 맞지 않는 결정이었다.
2. **원문의 말투를 살렸는가.** 07번. 문장은 틀리지 않았는데 원문의 가벼운 말투가 사라졌다.
3. **hook이 가장 중요한 내용을 잡았는가.** 10번, 그리고 03번의 메모.

변형본 결과와 나란히 놓고 읽어야 한다. 이 판정기는 "원문과 다르게 말했는가"는 잘 잡는다. 하지만 "이대로 내보낼 만한가"라는 사람의 판단과는 절반쯤만 맞았다. 틀린 대본을 거르는 장치이지, 좋은 대본을 고르는 장치는 아니다. 표본은 11편, 라벨을 매긴 사람은 한 명이다.

### 3.4 고정 뒤에 드러난 결함

test 원본 6편 가운데 2편(03, 06)이 `human_review`로 갔다. LLM은 두 편 모두 문제없다고 봤다. 걸린 이유는 근거 구절이 비어 있어서다. 03의 hook은 "예상과 다른 수치를 보였어요"처럼 궁금증만 거는 문장이고, 06의 마지막 섹션은 "여러분의 팀은 회의를 어떻게 진행하고 계신가요?"라는 질문이다. 둘 다 원문의 어느 구절에도 기대지 않는 문장이라 댈 구절이 없다.

판정기가 "문제없다고 한 섹션은 반드시 원문 구절을 대야 한다"고 요구한 것이 원인이다. 사실을 말하지 않는 섹션에는 맞지 않는 요구다. dev 6편에는 이런 문장이 없어서 조정하는 동안 드러나지 않았다. 고칠 방법은 분명하다(섹션마다 "사실 주장이 있는가"를 먼저 묻고, 없으면 구절을 요구하지 않는다). 하지만 test를 본 뒤에 고치면 test가 더는 처음 보는 묶음이 아니게 되므로 고치지 않았다. 고친다면 새 원문으로 다시 검증해야 한다.

## 4. 한계와 남은 일

### 4.1 확인하지 못한 것

- **표본.** 원문 12개는 모두 내가 AI 도구로 쓴 가상의 글이다. 실제 사용자가 넣는 글의 분포와 다를 것이다. 대본은 12편, 변형본은 18개다.
- **같은 계열 모델.** 원문과 변형본을 만드는 데 Claude를 썼고, 판정 모델도 Claude다. 같은 맹점을 공유할 수 있다. 변형본의 결함은 사람이 고른 한 군데 치환이라 정답 자체는 모델에 기대지 않지만, 다른 회사 모델로 판정해 보지는 않았다.
- **사람 라벨은 한 사람 것이고 11편이다.** 라벨 사이의 일치도는 잴 수 없었다. 6편은 댓글을 판정으로 옮겨 적은 것이다. 01번은 라벨을 매기기 전에 AI 도구에게서 "예상하지 못한 문제가 3개 나왔다"는 말을 들은 상태여서 비교에서 뺐다.
- **test 묶음이 완전히 가려지지는 않았다.** 화면에서 대본을 옮기는 과정에서 AI 도구가 test 대본 문장을 봤다. 그 대본에서 기준을 뽑지는 않았다.
- **hook의 매력은 보지 않는다.** 틀리지 않았는가만 본다. 03번 hook처럼 원문과 어긋나지는 않지만 맥이 빠지는 문장은 통과한다.
- **화면 제목(헤드라인)은 보지 못한다.** 승인 뒤에 따로 생성된다. 1번 대본의 헤드라인에도 "한산"이 들어 있었다.
- **분량 식은 한 가지 설정에서 쟀다.** Aria 1.1배속이다. 다른 목소리나 배속에서는 다시 재야 한다. 실제 영상 길이와는 한 편에서만 비교했다(예상 32.4초, 실제 0:33).
- **반복 일관성은 dev에서 3회만 쟀다.**
- **한글로 쓴 수(세 번, 두 대)와 계산해서 나온 숫자는 숫자 안전망이 다루지 못한다.**
- **모델 별칭.** `sonnet`이라는 이름이 가리키는 모델은 시간이 지나면 바뀐다. 검증한 때는 `claude-sonnet-5-5`였다.
- **기존 [사실 확인] 검수와 비교하지 못했다.** 초안 12편에 표시가 하나도 없어서 견줄 대상이 없었다.

### 4.2 시간이 더 있다면

1. **구절 요구를 고친다.** 3.4의 결함이다. "사실 주장이 있는 섹션"에만 근거 구절을 요구하고, 새 원문으로 다시 검증한다.
2. **라벨에서 나온 기준 세 가지를 넣는다.** 마지막 섹션이 행동을 권하는가, 원문의 말투를 살렸는가, hook이 가장 중요한 내용을 잡았는가. 앞의 것은 지금 경고로 나오는 역할 불일치를 탈락 사유로 올리는 일이고, 뒤의 둘은 새 질문이다. 사람 라벨을 더 모아 그 라벨에 맞춰 조정한다.
3. **원문 탓과 대본 탓을 나눈다.** 주제가 둘인 원문(02번)은 다시 뽑아도 같은 문제가 반복될 것이다. 이럴 때는 `regenerate`가 아니라 "원문을 나누거나 고르라"는 다른 행동이 필요하다. 라벨을 매기다가 알게 됐다.
4. **만족도 점수와 맞춰 본다.** 쇼더스는 결과 화면에서 1~5점 만족도를 받는다. 판정 결과와 이 점수의 관계를 보면, 지금은 가설인 기준을 실제 사용자 반응으로 고칠 수 있다.
5. **재생성까지 잇는다.** 사유를 생성기에 돌려주고 다시 뽑은 대본이 통과하는지 본다. 사유가 쓸모 있는지는 거기서 드러난다.
6. **쇼더스의 MCP와 이어 붙인다.** 쇼더스는 이미 Claude에 MCP로 붙는다. 판정기를 MCP 도구로 내는 얇은 서버(`mcp_server.py`)는 만들어 클라이언트로 호출까지 확인했다. "초안 읽기, 판정, 승인"을 쇼더스의 도구와 한 흐름으로 돌려 보는 것은 하지 못했다.
7. **분량 기준을 다시 정한다.** 실제 초안의 절반이 30초에 못 미치는 것이 생성기의 문제인지 목표 구간의 문제인지는 운영 데이터를 봐야 안다.
